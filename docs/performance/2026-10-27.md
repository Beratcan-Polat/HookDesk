# Local Docker baseline — 27 October 2026

I ran the full load-test profile against the isolated `hookdesk-load` stack. The normal development stack remained running on the same machine. These are local observations, not production capacity guarantees.

Artifacts: [raw JSON](2026-10-27-baseline.json), [standalone HTML report](2026-10-27-baseline.html). The [runbook](../runbooks/performance.md) documents the workload and reproduction commands.

## Environment

- Docker Desktop 29.9.2, Linux VM with 12 logical CPUs and 3.69 GiB available memory.
- PHP 8.4.27, Node.js 24.12.0, PostgreSQL 18 and Redis 8.
- `APP_DEBUG=false`, application code copied into the backend image, five-child PHP-FPM pools for the API and internal test receiver.
- Application source revision `c957ce400a34bdc461d6749f751e3a948b83315f`. The report also records the image ID and load-harness fingerprint.
- Request data includes 1,024 bytes of padding. Each routed event has one subscribed destination. Capacity-stage quota/rate overrides are listed in the JSON; the policy check uses defaults.
- Measurement window: `2026-10-27T08:49:41Z` to `2026-10-27T08:51:50Z`.

## Results

The run issued **711 event POST requests**: 706 returned `202`, and five expected policy-limit responses returned `429`. Idempotent duplicates were accepted without creating additional work. The database contained **691 unique events**, including 30 intentionally unrouted policy events. All **661 routed events** completed with exactly one attempt and one signature-verified receiver request. Quota counters matched distinct events. No generator-side drops or unexpected response statuses were recorded.

- **Concurrency 1, one worker, 40 events:** 15.28 requests/s; API p95 85.48 ms, p99 89.93 ms; total delivery p95 1 second.
- **Concurrency 5, one worker, 100 events:** 33.26 requests/s; API p95 209.77 ms, p99 253.99 ms; total delivery p95 4 seconds.
- **Concurrency 10, one worker, 100 events:** 33.40 requests/s; API p95 357.64 ms, p99 364.29 ms; total delivery p95 5 seconds.
- **Five requests/s for approximately 60 seconds:** all 300 events delivered; API p95 123.91 ms, p99 193.62 ms; total delivery p95 1 second.
- **Concurrency 10, three workers, 100 events:** 27.13 requests/s; API p95 454.86 ms, p99 487.10 ms; total delivery p95 1 second.
- **Sampled resources:** the largest observed aggregate memory use of load-test containers was 368.48 MiB. Full per-container CPU/memory samples are in the JSON.

The default-policy check filled 25 acceptance slots and then sent ten concurrent requests. Exactly 30 requests were accepted and five were rate-limited with `Retry-After`. Event reading remained available afterward. Sixteen duplicate requests in the idempotency stage produced one event, one delivery, one receipt and one usage increment.

## What I take from this run

Increasing request concurrency from five to ten did not materially increase acceptance throughput; API tail latency increased. Three workers shortened the delivery tail from five seconds to one second, while API response latency increased in that stage. This indicates a useful delivery/concurrency tradeoff on this machine, without identifying a specific database or PHP bottleneck. SQL/lock profiling and repeated runs on a dedicated host are needed before attributing the plateau to one component.

Queue and total delivery times use one-second-resolution application timestamps. Outbound HTTP durations and client API latencies are measured separately in milliseconds. Resource values are sampled observations. The one-minute steady workload is not a multi-hour soak test.
